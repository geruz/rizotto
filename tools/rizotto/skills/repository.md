# Repositories

The repository is the only package of a service that talks to the database.
Everything above it — the RPC implementation, the controller — works with Go
types and never sees a `pgx` call.

    services/order/repository/order-repository.go   the hand-written methods
    services/order/repository/sql/schema.sql        the schema sqlc type-checks against
    services/order/repository/sql/order-queries.sql the annotated queries
    services/order/repository/db/                   generated by sqlc — never edit
    services/order/repository/migrations/           dbmate migrations

`rizotto service add -db yes` scaffolds all five for a new service.

## Column conventions

These two are the defaults. Depart from them only when the task says to, and
say so in the migration when you do.

### 1. Time is stored without a time zone, in UTC

`TIMESTAMP` — never `TIMESTAMPTZ` — unless the task explicitly calls for a zone:

```sql
created_at TIMESTAMP NOT NULL DEFAULT NOW(),
updated_at TIMESTAMP NOT NULL DEFAULT NOW()
```

sqlc maps it to `pgtype.Timestamp`, whose `.Time` is the value as stored, with
no zone conversion in the way. Everything written to such a column is UTC, so
convert at the edges — `t.UTC()` on the way in, format for the caller's zone on
the way out — and never in the repository.

`TIMESTAMPTZ` would make Postgres convert on read using the session `TimeZone`,
so the same row would come back differently depending on who connects. That is
why it is not the default.

### 2. Integers are stored as 64-bit

`BIGSERIAL` for identity columns, `BIGINT` for other integers, unless the task
says otherwise:

```sql
CREATE TABLE public.orders (
    id BIGSERIAL PRIMARY KEY,
    ...
);
```

sqlc maps `bigint` to Go `int64`, which is the same width as the `int` used in
the client types. Widening `int` → `int64` is lossless on every platform the
framework supports, so the conversion needs no bounds check:

```go
func toOrderID(id int) (int64, bb.ServiceError) {
    if id <= 0 {
        return 0, bb.NewInvalidRequestError("invalid order id")
    }

    return int64(id), nil
}
```

With `SERIAL`/`int32` the same function has to reject anything above
`math.MaxInt32`, and every service repeats that check — plus a widening
migration once the table outgrows 2.1 billion rows. `BIGSERIAL` removes both.

`LIMIT`/`OFFSET` are the one place this is not automatic: sqlc types a bare
`$1` placeholder as `int32`, because nothing in the statement tells it
otherwise. Cast it, and name it so the generated field keeps its name:

```sql
-- name: SelectOrders :many
SELECT *
FROM public.orders
ORDER BY created_at DESC, id DESC
LIMIT sqlc.arg('limit')::bigint OFFSET sqlc.arg('offset')::bigint;
```

That yields `SelectOrdersParams{Offset int64, Limit int64}`. Without the cast
the repository takes `int32` and the service is back to clamping at
`math.MaxInt32`.

Use a narrower column only for something genuinely bounded and stored in bulk —
an enum-like code, a small counter — and then keep the narrowing conversion at
the repository boundary rather than leaking `int32` upwards.

## Ordering and pagination

Order by a unique key, or add one as a tiebreaker. `created_at` alone is not
unique: `NOW()` is the transaction start time, so every row inserted by one
transaction — a batch import, a seeder, a data migration — gets a byte-identical
value, and the order within that group is undefined. Across two requests it can
differ, and rows then duplicate and vanish at page boundaries.

```sql
ORDER BY created_at DESC, id DESC
```

Index the exact ordering, or every listing is a sequential scan plus a sort:

```sql
CREATE INDEX orders_created_at_id_idx ON public.orders (created_at DESC, id DESC);
```

## Writing a query

Queries live in `repository/sql/<service>-queries.sql`, annotated for sqlc:

```sql
-- name: GetOrder :one
SELECT *
FROM public.orders
WHERE id = $1;

-- name: CreateOrder :one
INSERT INTO public.orders (name)
VALUES ($1)
RETURNING *;
```

`:one` returns a row, `:many` a slice, `:exec` nothing. `RETURNING *` on writes
gives the caller the stored row — including the generated `id` and the
defaulted timestamps — without a second round trip.

Run `task gen` after every edit. It runs sqlc in docker against `sqlc.yaml`,
which has one entry per service, and rewrites `repository/db/`. That directory
is generated: fix the `.sql` file and regenerate, never the `.go`.

## Wrapping it in a method

The repository embeds `pg.Repository` and holds the generated `*db.Queries`:

```go
type OrderRepository struct {
    pg.Repository

    queries *db.Queries
}

func NewOrderRepository(pool *pgxpool.Pool) OrderRepository {
    return OrderRepository{Repository: pg.NewRepository(pool), queries: db.New(pool)}
}

func (r OrderRepository) GetOrderByID(ctx context.Context, id int64) (db.Order, error) {
    return r.queries.GetOrder(ctx, id)
}
```

Methods return `db.<Model>` and a plain `error`. Translating those into
`bb.ServiceError` is the service's job, using the classifiers:

```go
pg.IsNotFoundError(err)   // pgx.ErrNoRows or sql.ErrNoRows
pg.IsDuplicateError(err)  // unique violation, SQLSTATE 23505
```

A repository that returned `bb.NotFoundError` itself would decide the HTTP
status of a row that is missing — which is the service's call, not the
storage layer's.

## Transactions

`WithTx` rebinds the generated queries onto an open transaction:

```go
tx, err := pg.NewTransaction(ctx, r.Conn())
if err != nil {
    return err
}
defer func() { _ = tx.Close(ctx) }()

qtx := r.queries.WithTx(tx.Tx())
// ... calls on qtx are inside the transaction
return tx.Commit(ctx)
```

`Close` rolls back when no savepoint is set, so a deferred `Close` after a
successful `Commit` is a no-op. `SavePoint` / `RollbackToSavePoint` handle
nesting.

## Changing the schema

Every change is two edits that must agree:

1. a new file in `repository/migrations/`, created by
   `task migrate-new -- <service> <name>` and applied by `task migrate-up`;
2. the matching change in `repository/sql/schema.sql`, which is what sqlc reads.

Editing only the migration leaves sqlc type-checking against the old shape;
editing only `schema.sql` generates code for columns the database does not
have. Migrations are `dbmate` files with both directions:

```sql
-- migrate:up
ALTER TABLE public.orders ADD COLUMN IF NOT EXISTS total BIGINT NOT NULL DEFAULT 0;

-- migrate:down
ALTER TABLE public.orders DROP COLUMN IF EXISTS total;
```

`scripts/migrate.sh` walks `services/*/repository/migrations` and runs dbmate per
service against its own `public.dbmate_migrations_<service>` table, so services
do not share migration state. A new service is picked up by the glob with no
edit. The `migrate-*` tasks run it in docker against the local PostgreSQL of
`docker-compose.yml`; a deploy runs it from the image of
`.docker/migrations.Dockerfile`.

Never edit a migration that has been applied anywhere — add a new one. What a
migration may do while the previous release is still running, and how to remove
a column, is in `.agents/skills/database/SKILL.md` at the project root: read it
before the first migration of a change.

## Checklist for a new table

- `id BIGSERIAL PRIMARY KEY`
- `created_at` / `updated_at` as `TIMESTAMP NOT NULL DEFAULT NOW()`
- an index for every ordering a listing uses, tiebroken by `id`
- the same DDL in both the migration and `repository/sql/schema.sql`
- `task gen`, then `task migrate-up`, then `task migrate-redo -- <service>` to
  prove the `down`
